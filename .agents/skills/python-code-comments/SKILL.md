# Python 代码注释

## 目标

让 Python 代码尽可能自解释，只保留能降低维护风险的注释。

按以下优先级处理可读性问题：

1. 先改善命名、控制流和代码结构。
2. 再用类型标注、明确的异常、测试或断言表达机器可验证的事实。
3. 最后用注释补充代码本身无法充分表达的信息。

注释应主要回答以下问题之一：

- 为什么必须这样实现？
- 这里依赖什么不变量、前置条件或顺序约束？
- 哪个业务规则、外部协议或兼容要求导致了这段看似奇怪的代码？
- 这里刻意接受了什么性能、安全性、一致性或可维护性取舍？
- 哪种边界情况容易被未来维护者误改？

不要用注释逐行翻译 Python 代码。

## 工作边界

- 开始前读取适用的 `AGENTS.md`、`CONTRIBUTING.md`、项目文档和相邻代码，确认注释语言与 docstring 格式。
- 仓库明确约定优先于本 Skill；没有明确约定时，保持与相邻代码一致。
- 只做消除注释噪声或准确表达意图所必需的最小代码调整，不借机进行无关重构。
- 不添加依赖、检查器、格式化器或项目配置。
- 不把 README、教程、API 参考、提交说明或设计决策文档改造成源码注释。
- 不为达到“注释覆盖率”而添加注释；注释数量不是质量指标。

## 工作流

1. **确定范围**
   - 找出用户要求修改的文件、符号和代码路径。
   - 同时检查与改动代码相邻的现有注释，避免新旧描述互相矛盾。

2. **先判断代码是否应自解释**
   - 可以通过更准确的名称、小范围提取函数或简化条件解决时，优先改代码。
   - 不要为了保留糟糕命名而增加解释性注释。

3. **为每条候选信息选择载体**
   - 调用者可依赖的行为契约：docstring。
   - 实现者需要知道的原因、限制或不变量：块注释。
   - 单行局部且不明显的事实：行尾注释。
   - 临时技术债：可追踪的 `TODO`。
   - 工具控制：保留为机器指令注释，不当作普通说明文字。
   - 从代码即可直接看出：不写注释。

4. **添加、改写或删除**
   - 同等重视删除无价值、过时、重复或误导性的注释。
   - 将注释放在它所约束的最小代码范围附近。

5. **复核**
   - 按当前实现逐条核对注释，不根据旧实现或猜测补写事实。
   - 检查改动后的 docstring、字符串和指令注释没有破坏语法。
   - 使用仓库已有的相关验证命令；不要为了本 Skill 引入新工具。

## 注释决策规则

对每条注释执行以下检查：

### 删除测试

删除该注释后，熟悉 Python 但不了解当前业务背景的维护者是否会失去重要信息？

- 不会：删除注释。
- 会：继续检查其准确性、位置与表达方式。

### 持久性测试

注释是否描述稳定的意图或约束，而不是当前实现的偶然细节？

优先记录：

- 业务语义和数据不变量。
- 并发、事务、锁和资源生命周期要求。
- 排序、去重、幂等性和重试边界。
- 时间单位、时区、编码、精度和舍入规则。
- 外部 API、文件格式、数据库或历史数据的兼容限制。
- 安全性与性能相关的非显然取舍。
- 看似可以简化、实际不能简化的原因。

避免记录：

- 变量赋值、循环、条件判断和函数调用正在做什么。
- 可以从名称、类型标注、常量或函数签名直接得出的信息。
- 当前行号、作者、修改日期或版本历史。
- 没有证据的推测、道歉或“以后也许会用到”。

### 可执行性测试

能被代码、类型、测试或断言可靠表达的规则，不应只存在于注释中。

- 用测试固定回归行为。
- 用断言保护真正的不变量。
- 用类型标注表达数据形状。
- 用异常和错误消息表达运行时失败。
- 注释只解释这些机制背后的原因与边界。

## Docstring

### 何时需要

为以下对象编写或保留 docstring：

- 公共模块、类、函数和方法。
- 行为、约束或副作用不明显的非公共函数与方法。
- 需要调用者在不阅读实现的情况下正确使用的接口。

名称和签名已经完整表达行为的简单私有辅助函数，可以不写 docstring。

### 内容

Docstring 描述调用者可依赖的契约，而不是逐步解释实现。按适用情况说明：

- 对象代表什么，或函数完成什么语义操作。
- 参数的业务含义、有效范围、单位和特殊值。
- 返回值的语义、顺序、稳定性或所有权，而不是仅重复类型。
- 可观察副作用，例如修改参数、写入存储、发起网络请求或改变缓存。
- 调用者需要处理的异常。
- 幂等性、线程安全、重入性、事务性和生命周期限制。
- 与外部系统或持久化格式相关的兼容契约。

不要：

- 重复函数名、参数名、类型标注和默认值已经表达的信息。
- 写“这是一个类”“该函数返回一个字符串”之类的空洞描述。
- 把仅与实现维护者相关的局部算法细节塞进公共 docstring。
- 为继承而来的行为复制基类 docstring；只说明实质差异。

### 格式

- 始终使用三重双引号 `"""`。
- 首行给出独立、准确的摘要。
- 多行 docstring 在摘要后空一行，结束引号独占一行。
- 保持仓库既有的 Google、NumPy、Sphinx 或简洁自然语言格式，不在同一项目中另创新格式。
- 若项目使用参数章节，描述参数语义，不重复类型标注。
- 同一文件内保持祈使式或描述式语气一致。

## 块注释

块注释用于解释紧随其后的复杂代码：

- 与代码保持相同缩进。
- 每行使用 `# ` 开头。
- 放在被解释代码之前，而不是远离代码集中写一大段说明。
- 多句说明使用完整、连贯的句子。
- 一个注释只覆盖一个清晰主题；过长时应考虑改善设计或移入设计文档。

优先解释原因和不变量：

```python
# 在写入 outbox 记录前保持事务打开；否则进程在提交后、发布前崩溃时，
# 事件可能永久丢失。
with transaction():
    save_order(order)
    save_outbox_event(event)
```

不要描述控制流：

```python
# 遍历所有订单并处理每个订单。
for order in orders:
    process(order)
```

上例应直接删除注释。

## 行尾注释

只在局部事实确实不明显、且一句短注释足够时使用：

```python
mask = value & -value  # 提取最低位的已置位比特。
```

规则：

- 谨慎使用；复杂解释改为代码前的块注释。
- 代码与 `#` 之间至少保留两个空格，`#` 后保留一个空格。
- 不为了视觉对齐而在连续行中填充空格。
- 不重复当前语句已经明确表达的动作。

## TODO 注释

`TODO` 只表示已知且暂时保留的技术债、兼容分支或不完整方案，不充当个人备忘录。

优先格式：

```python
# TODO: GH-123 - 所有客户端迁移到 schema v2 后删除旧格式回退逻辑。
```

每个新 `TODO` 应尽可能包含：

- 真实存在的 issue、工单或规范引用。
- 明确且可执行的后续动作。
- 可判断的删除条件、截止事件或失败原因。

不要：

- 编造 issue 编号、链接、负责人或截止日期。
- 只写 `# TODO: fix this`、`# FIXME` 或“以后优化”。
- 仅用个人姓名或团队名代替可追踪上下文。
- 在已有任务系统能够承载全部信息时复制一份会过期的长描述。

没有真实跟踪引用或明确退出条件时，不随意新增 `TODO`；在最终说明中指出缺失的跟踪信息。

## 机器指令注释

`# type: ignore`、`# noqa`、`# pragma`、格式化开关和覆盖率标记等是机器指令，不是普通注释。

处理规则：

- 优先修复根因，不用抑制注释隐藏真实问题。
- 必须抑制时，限制到最小代码范围和最具体的诊断规则。
- 不新增文件级或大范围禁用，除非仓库已有明确政策或用户明确要求。
- 非显然的抑制原因使用相邻普通注释说明；不要破坏工具要求的固定语法。
- 未运行对应的现有验证前，不删除或扩大指令注释。
- 不把旧式类型注释当作文档；现代代码优先使用正常类型标注。

## 注释语言

- 首先遵循仓库语言政策，其次匹配相邻代码。
- 中文优先项目使用简洁、自然的简体中文。
- 标识符、异常名、协议名、字段名和标准术语保持原始拼写，不强行翻译。
- 面向国际协作且仓库要求英文时使用清晰英文。
- 不在同一段中无必要地来回切换语言。
- 中文自然语言可以使用中文标点；代码片段、标识符和机器指令中的语法字符必须保持半角原样。

## 禁止模式

不要生成或保留以下注释：

```python
# 创建用户。
user = User()

# 如果启用了缓存。
if cache_enabled:
    ...

# 返回结果。
return result
```

还应删除：

- 被注释掉的旧代码。
- 仅用于分隔显而易见代码段的巨大横幅。
- 与实现矛盾或无法验证的承诺。
- 记录“某人于某日修改”的历史注释。
- 对错误命名和过深嵌套的补丁式说明。
- 与 docstring、类型标注或相邻注释重复的内容。
- 包含密钥、令牌、个人数据或其他敏感信息的注释。

## 审查清单

完成修改前逐项确认：

- [ ] 每条注释都提供代码本身无法直接表达的重要信息。
- [ ] 注释与当前实现一致，不依赖已经删除或计划中的行为。
- [ ] 能通过命名、类型、测试或断言表达的事实没有只写在注释里。
- [ ] Docstring 描述调用契约，而不是实现步骤。
- [ ] 公共行为中的副作用、异常、单位和兼容限制按需说明。
- [ ] 块注释与被解释代码相邻，行尾注释使用克制。
- [ ] 新 `TODO` 可追踪、可执行且没有虚构引用。
- [ ] 机器指令注释范围足够窄，没有用来掩盖根因。
- [ ] 没有注释掉的代码、修改历史、重复说明或敏感信息。
- [ ] 语言、标点和 docstring 格式与仓库一致。
- [ ] 相关代码变化后，同步更新或删除了受影响的旧注释。

## 完成标准

当用户要求实际修改代码时：

- 直接完成必要的注释添加、改写和删除，而不只给建议。
- 保持改动最小，不改变未被要求的运行时行为。
- 在最终回复中简要说明新增了哪些关键解释、删除了哪些噪声，以及是否存在无法确认的约束或缺少跟踪信息的 `TODO`。
