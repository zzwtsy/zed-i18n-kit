# 清理推理过程泄漏

推理过程泄漏是指持久文本采用作者会话而非仓库当前状态的视角：引用只有当时对话才能解析的编号，叙述一次 PR 或评审的过程，或者保留已经失去所有者的计划与辩解。目标不是单纯缩短文字，而是让读者只依赖当前 checkout 中可解析的证据，就能理解并验证每个保留的事实。

本 skill 是指导规则，不是自动改写脚本。它改编自 DeepSeek Harness 的同名流程；来源与许可见 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)。

## 输入与授权

- 要求明确的文件、目录或文档类别范围；不能从“清理一下”推断为全仓库扫描。
- `audit`、`review`、`检查`或`找问题`只报告 findings，不编辑文件。
- 只有用户明确要求 `fix`、`trim`、`清理`或`改写`时才编辑，并保持在指定范围内。
- 开始前读取适用的 [AGENTS.md](../../../AGENTS.md) 和范围内的权威文档。聊天记录、临时计划和旧 patch 不能成为持久引用的唯一所有者。
- 默认排除 `.git/`、`.venv/`、`local/zed/`、派生工作区、构建产物、受控 corpus、fixtures 和 snapshots。用户明确指定 `local/zed/` 时只能只读审计；派生数据应追溯并修改拥有它的源码或生成器。
- Python 注释或 docstring 的载体选择、位置和格式同时遵循 [python-code-comments](../python-code-comments/SKILL.md)。

## 核心判断

对每个可疑段落询问：

> 只查看当前 checkout，不访问会话记录、PR 讨论或未提交草稿的读者，能否解析每个引用并验证每项声明？

如果不能，先列出段落承载的完整命题，再按仓库当前视角重述仍然成立的事实，最后删除会话叙事。只有完全不承载事实的审计编号、控制流复述或空洞辩解才直接删除。

一个完整命题按实际情况保留：

- 主体、动作和对象；
- 条件、时机、顺序与例外；
- `must`、`may`、`never` 等强度；
- 所有权、副作用、失败方式与后果；
- 测量数据或外部约束的来源。

减少字数不能作为删除事实、改变义务强度或把假设写成已交付能力的理由。

## 泄漏类型

1. **失效的会话引用**：`decision 7`、`audit C2`、未提交设计的 `§3.2`、会话阶段标签。存在已提交所有者时改为名称和路径；不存在时删除引用并保留事实。
2. **PR、提交或评审视角**：`this PR adds`、`上一轮评审认为`、`前一个 commit`。在当前状态文档中陈述已交付机制；历史证据只留在允许记录历史的 completed 工作项、ADR 或 postmortem 中。
3. **变化流水账和索引式版本戳**：`used to`、`不再`、`现在`、`本版`、`this cut`。README、设计文档和 docstring 陈述当前行为；有价值的回归原因改为现在时反事实，例如“缺少 X 时会发生 Y”。
4. **面向 reviewer 的辩解**：`reviewer confirmed`、`这是正确的，因为……`、`这个 cast 很安全`。改写为维护者需要的不变量、前置条件或失败后果；代码或测试已清楚表达时删除。
5. **控制流、测试和推导复述**：`先做 X，再做 Y` 或逐步转述测试主体。删除显而易见的过程，只保留非显然契约、测试设计原因和保护条件。
6. **对冲与无主计划残留**：`probably fine for now`、`应该够用`、没有 issue 或退出条件的延期。用可验证边界重述；真实技术债应进入已有工作项、issue 或带明确退出条件的 `TODO`，不能编造引用。
7. **写作语言或草稿残留**：与所在表面语言不一致的工作语言片段、私有分隔符、草稿标记。翻译为仓库约定语言、替换为可解析的外部名称，或在不承载事实时删除。

## 不应删除的内容

以下内容可能命中 probes，但不是泄漏：

- 当前 checkout 可解析的 ADR、工作项、issue、标准章节和固定外部资料引用；
- completed 工作项、ADR 备选方案和 postmortem 中为其文体所需的历史与验证证据；
- `noqa`、`type: ignore`、coverage ignore 等机器指令旁真实且必要的抑制原因；
- “缺少 X 时会发生 Y”这类现在时回归保护说明；
- 带来源的测量边界，例如“实测最大样本为 48 KiB”；
- 描述同一运行时中两个对象的“旧连接/新连接”，以及询问当前日期的自然时间用语；
- 流程文档对一般 PR、review 或 release 规则的说明；
- 协议名、schema 名、路径中的 `v1` 等稳定标识符。

需要校准边界或判断删改风险时，读取[语义示例](references/examples.md)。

## 工作流

1. 确认范围、授权类型、适用 `AGENTS.md`、权威所有者和默认排除项。
2. 只读审计优先。运行 [recall probes](references/recall-batteries.md)，先用一个已知正例和一个近似反例校准每类模式，再逐条做语义判断。
3. 不依赖模式完成审计：阅读范围内文字最密集、契约最重要的部分，例如 README、设计文档、公共 docstring、复杂模块注释、工作项和 ADR。
4. 将候选分类为 `keep`、`restate`、`delete` 或 `defer`。删除前逐项列出命题，并检查[过度纠正陷阱](references/examples.md#过度纠正陷阱)。
5. 先改所有者，再处理派生物。生成 catalog、manifest、snapshot 或 fixture 命中时，追溯源码、schema、模板或场景；只有行为变化获得授权时才重新生成派生物。
6. 获得编辑授权后只应用明确修改。用户可见或模型可见文字属于行为，不能混入纯文案清理；缺少行为证据时保留并报告延期。
7. 重新运行 probes，确认剩余命中均为 deliberate keeps；检查每个保留引用在当前 checkout 可解析，并运行受影响表面的聚焦检查。文档至少运行 `git diff --check` 和相对链接检查；Python 源码变化运行 `uv run python scripts/check.py`。

## 交付

报告实际检查范围、明确修改、deliberate keeps、延期项和运行过的精确命令。模式零命中不等于审计通过；未做无模式阅读或未运行的检查必须明确说明。
