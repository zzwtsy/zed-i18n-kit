# 现代 Python 最佳实践

## 目标

编写自然、明确、可靠且易于维护的 Python 代码。优先保证行为正确和设计清晰，再考虑抽象、性能或技巧性写法。

遵循仓库现有约定和项目支持的最低 Python 版本。不要为了套用某条规则而破坏公共 API、运行时行为、兼容性或局部一致性。

当任务涉及版本特性、弃用状态或规则冲突且仓库无法给出答案时，再读取 `references/official-sources.md` 并查阅对应官方资料；普通任务不必加载该文件。

## 边界与配合关系

本 Skill 负责 Python 代码本身的通用设计与实现质量：

- 不安装、替换或配置包管理器、格式化器、代码检查器、类型检查器或测试框架。
- 不负责打包、发布、Git 提交、版本号、CI 平台或项目脚手架。
- 不把纯静态类型问题扩展到本 Skill；泛型、`Protocol`、`TypedDict`、类型收窄和 `Any` 治理由 `python-strong-typing` 负责。
- 不把纯性能调优、纯安全审计或纯文档写作伪装成一般重构；只应用与当前实现直接相关的基础规则。
- 可以与 `python-strong-typing` 同时使用，但两份 Skill 各自保持职责边界。

## 开始前

1. 阅读相关源码、调用方、测试、配置和公共入口，先理解真实行为与约束。
2. 从 `pyproject.toml`、CI、容器或运行时配置确定最低 Python 版本。
3. 识别公共 API、持久化格式、异常契约、外部副作用和兼容性要求。
4. 找出当前任务必须解决的问题，避免顺带清理无关代码。
5. 优先使用仓库现有抽象和标准库；新增依赖必须由任务本身明确要求或具有不可替代的收益。

## 修改策略

- 做最小但完整的改动，不留下半迁移状态、双重实现或无调用路径的旧代码。
- 保持行为不变，除非用户明确要求改变行为；发现潜在行为变化时主动说明。
- 先修复根因，再处理症状；不要通过宽泛异常捕获、静默回退或额外状态掩盖设计问题。
- 保持局部一致性。仓库已有合理惯例时，不为了个人偏好制造第三种写法。
- 删除因本次修改而失效的代码、分支、导入和注释，但不扩大到无关模块。

## 兼容性与现代化

- 只使用最低 Python 版本支持的语法和标准库 API。
- 优先使用稳定、公开的语言特性和标准库接口，不依赖以下内容：
  - 以单下划线开头的第三方或标准库私有实现。
  - 已弃用、软弃用或明确计划移除的 API。
  - CPython 偶然行为、对象布局或未文档化副作用。
- 不为了使用更新语法而提高项目最低版本。
- 对版本相关写法，优先采用仓库已有兼容策略，而不是散布运行时版本判断。
- 可执行模块将启动逻辑放入明确入口，避免导入模块时自动执行网络、文件写入、进程启动或其他不可逆副作用。

## 可读性与结构

- 选择能直接表达领域意图的名称，避免无信息量的 `data`、`info`、`obj`、`tmp`、`manager` 和 `utils`。
- 一个函数承担一个连贯职责；当函数同时处理解析、校验、业务决策和 I/O 时，按真实边界拆分。
- 不为一两行显而易见的代码创建无语义包装，也不为未来猜测提前建立抽象层。
- 优先使用提前返回、守卫条件和小型辅助函数减少深层嵌套；不要把控制流拆得支离破碎。
- 保持模块边界清晰：领域逻辑不应直接依赖命令行、HTTP、数据库驱动或全局配置细节。
- 优先显式导入。避免通配符导入、循环导入和仅为绕过循环依赖而散布局部导入。
- 只有在确实维护公共导出面时定义 `__all__`；不要把它当作隐藏糟糕模块边界的手段。
- 使用组合表达可替换行为；只有存在真实的“是一个”关系和稳定扩展契约时使用继承。

## 函数与 API 设计

- 保持签名小而明确。必需输入与可选策略分开，相关参数不要依赖隐含顺序或共享全局状态。
- 对容易混淆的布尔值、模式、单位和策略参数，优先使用关键字参数；行为明显分叉时使用枚举、策略对象或独立函数，而不是堆叠布尔开关。
- 返回稳定、可预测的形状。不要在成功分支返回对象、失败分支返回魔法值、特殊分支返回不同长度元组。
- 当多个返回值具有长期语义时，使用具名记录或领域对象；短小且局部的一次性解包可保留元组。
- 在系统边界解析和校验输入，内部代码依赖已建立的不变量；不要让每层重复猜测数据是否合法。
- 副作用必须从名称、位置或 API 契约中可见。读取函数不应暗中写入，计算函数不应暗中修改调用方对象。
- 对可选值区分“未提供”和“明确提供空值”。当 `None` 本身具有业务含义时，使用私有哨兵对象。
- 不把全局单例、环境变量或当前工作目录作为隐式依赖；在边界读取后显式传入需要的值。

## 数据建模与可变性

- 简单计算优先使用函数和内置数据结构；需要名称明确的记录时使用 `dataclass` 或适合的领域类。
- 具有不变量、行为、生命周期或资源所有权的数据使用类；不要把所有字典机械转换为类。
- 封闭且需要运行时身份的状态集合使用枚举，避免散落的魔法字符串和数字。
- 不使用可变对象作为函数默认值或共享类级默认值。需要新实例时使用延迟创建或 `default_factory`。
- 值对象在语义上不可变时才使用不可变设计；不要仅为显得现代而使用冻结对象。
- 明确区分原地修改与返回新值。调用方不应依赖隐藏的别名修改。
- 复制数据前先确认所有权和深浅复制语义；不要用 `deepcopy` 逃避对象边界设计。
- `slots` 只在确认动态属性、弱引用、序列化和继承兼容性后使用，并且应有明确收益。

## 控制流、集合与迭代

- 使用 `enumerate`、`zip`、`any`、`all`、`sum`、集合运算和字典查找表达常见意图，避免手写索引和状态变量。
- 当两个可迭代对象必须等长且版本支持时，使用 `zip(..., strict=True)` 暴露长度错误。
- 简单映射或过滤使用推导式；包含多层条件、副作用或复杂异常处理时改用普通循环。
- 对大数据、流式输入或只消费一次的结果使用迭代器和生成器，避免无必要地一次性物化。
- 不在迭代同一集合时进行会改变遍历结构的修改，除非基于副本或算法明确保证安全。
- 频繁成员测试使用集合或字典；但不要在数据规模未知时为微小常数差异牺牲清晰度。
- 模式匹配用于稳定、封闭且结构明确的数据分派；不要用复杂 `match` 替代简单条件。

## 异常处理

- 捕获能够实际处理的最窄异常类型，保持 `try` 块尽可能小。
- 不使用裸 `except`。除进程、任务或请求顶层边界外，通常不要捕获所有 `Exception`。
- 不捕获 `BaseException`，除非正在实现必须处理取消、退出和中断语义的基础设施。
- 预期失败使用清晰的返回协议或领域异常；不要用异常控制普通高频分支，也不要用魔法值吞掉真正错误。
- 转换底层异常时使用异常链，保留原始原因；只有明确不希望暴露实现细节时才抑制上下文。
- 异常消息说明失败操作和必要上下文，但不包含密钥、令牌、完整凭据或敏感载荷。
- 记录异常后若不能恢复，重新抛出；不要在多个层级重复记录同一异常。
- 不在 `finally` 中 `return`、`break` 或静默覆盖正在传播的异常。
- 清理资源优先使用上下文管理器，而不是依赖复杂的 `try/finally` 或析构器。

## 资源、文件与外部 I/O

- 文件、锁、连接、事务和临时资源使用 `with` 或异步上下文管理器管理生命周期。
- 多个动态资源使用 `ExitStack` 或 `AsyncExitStack`，避免手工维护脆弱的嵌套清理逻辑。
- 文本文件显式指定编码；需要跨平台稳定行为时同时明确换行和错误处理策略。
- 路径运算优先使用 `pathlib.Path`，不要手工拼接分隔符或依赖当前工作目录。
- 读取包内资源使用 `importlib.resources`，不要假设资源始终存在于普通文件系统路径。
- 数据损坏风险较高的写入先写入同目录临时文件，再通过原子替换提交；同时正确处理权限和清理。
- 网络、数据库和子进程调用设置明确超时。重试必须有上限，只用于可安全重试的操作，并保留最终错误。
- 调用子进程时优先传入参数序列并保持 `shell=False`；根据语义使用返回码检查、文本编码和超时。
- 不依赖 `__del__` 释放关键资源；资源所有者必须有确定的关闭路径。

## 并发与异步

- 只有存在真实并发需求时引入异步、线程或进程，不为普通顺序代码增加调度复杂度。
- I/O 并发优先使用异步或线程；CPU 密集任务根据隔离、序列化成本和运行环境选择进程、解释器或原生实现。
- 异步代码不得直接执行长时间阻塞 I/O 或 CPU 工作；无法替换的短期阻塞调用应明确转移到线程或其他执行器。
- Python 3.11+ 的相关新代码优先使用 `TaskGroup` 表达有所有权的并发任务；不要创建无人负责关闭和收集结果的后台任务。
- 设置超时并保持取消可传播。捕获取消异常后只做必要清理，然后继续传播，除非协议明确要求转换。
- 共享可变状态使用锁、队列、消息传递或所有权边界保护；不要把 GIL 当作同步机制。
- 并发任务失败时定义清楚：哪些任务取消、哪些结果保留、错误如何聚合，以及资源如何关闭。

## 日志与可观测性

- 模块使用 `logging.getLogger(__name__)`；应用程序在入口统一配置日志，库代码不擅自调用全局配置。
- 使用参数化日志而不是提前格式化字符串，让日志系统决定是否构造消息。
- 只在能够增加上下文或做出处理决策的层级记录日志，避免同一错误在每层重复输出。
- 记录异常堆栈时使用适合的异常日志接口，不手工拼接 traceback。
- 日志包含可诊断的操作、标识和状态，但必须脱敏密钥、令牌、Cookie、认证头和敏感业务数据。
- 高频路径避免无界日志和高基数标签；调试细节与面向用户的错误消息分离。

## 时间、数字与随机性

- 表示真实时间点时使用带时区的时间对象；系统内部通常统一为 UTC，在边界转换展示时区。
- 测量耗时、截止期限和退避间隔时使用单调时钟，不使用可能被系统校时修改的墙上时钟。
- 需要十进制精确语义的金额和计费数据使用 `Decimal` 或领域定义的整数最小单位，不依赖二进制浮点精确相等。
- 浮点近似比较使用容差策略，不直接依赖 `==` 表达数值近似。
- 安全令牌、密码重置码和不可预测标识使用 `secrets`，不要使用普通伪随机模块。

## 安全边界

- 把网络输入、环境变量、命令行、文件、数据库结果和反序列化内容视为不可信数据，在边界验证后再进入领域逻辑。
- 不对不可信输入使用 `eval`、`exec` 或可执行表达式机制。
- 不反序列化来源不可信的 `pickle` 数据，也不把反序列化当作校验。
- 文件路径来自外部输入时，验证允许根目录、规范化结果和符号链接策略，防止越界访问。
- SQL 使用参数绑定；Shell 避免解释器拼接；模板按输出上下文转义；把不可信文本作为正则字面量时使用 `re.escape`，并限制可控正则的复杂度。
- 临时文件和权限采用最小暴露原则；密钥不进入源码、日志、异常或测试快照。

## 性能与复杂度

- 先保证正确和清晰。只有证据表明存在瓶颈时才引入缓存、批处理、并发或低层优化。
- 优先修复算法复杂度、重复 I/O、无界物化和 N+1 调用，而不是追逐语法级微优化。
- 处理可能无界的数据时采用流式和背压设计，明确内存上限、批大小和超时。
- 缓存必须定义键、生命周期、容量、失效和并发语义；不要创建永久增长的隐式全局缓存。
- 优化前后使用仓库已有基准或可重复测量验证，不凭直觉声称更快。

## 注释、文档与可测试性

- 注释解释“为什么”、不变量、兼容性约束和反直觉取舍，不逐行复述代码。
- 公共 API、复杂协议和重要副作用应有与仓库风格一致的文档；不要在文档中复制容易失效的实现细节。
- 修改行为时同步更新相关注释、文档示例和错误消息，删除失效说明。
- 将时间、随机、网络、文件系统和外部服务隔离在边界，方便测试而无需全局猴子补丁。
- 行为变更或缺陷修复应按仓库既有框架补充聚焦的回归测试；不要顺带替换测试栈。

## 完成标准

完成修改前确认：

- 代码兼容项目最低 Python 版本，未引入私有、弃用或未文档化 API。
- 模块、函数和对象边界清晰，没有新增隐式全局状态或导入时副作用。
- 默认值、所有权、可变性和返回形状具有明确语义。
- 异常只在能够处理的层级捕获，错误原因、清理和日志行为正确。
- 文件、连接、锁、任务和子进程都有确定的生命周期、超时和关闭路径。
- 并发代码有所有权、取消、失败传播和共享状态策略。
- 不可信数据在边界验证，敏感信息不会进入日志或异常。
- 复杂度与性能改动有实际依据，没有以晦涩技巧换取未经验证的收益。
- 已运行仓库现有的相关测试和检查；无法执行的项目必须如实说明。

## 输出要求

- 说明关键设计选择、行为变化和兼容性影响。
- 报告执行过的验证命令及结果，不声称未执行的检查已通过。
- 列出仍存在但超出本次范围的风险，不顺带扩大修改。
