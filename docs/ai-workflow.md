# AI 开发工作流

## 1. 目标

本项目默认由 AI 协助调查、设计、实现、验证和复核。工程目标不是让 Agent 获得无限自主权，而是让每次修改都有稳定输入、有限范围、可运行证据和明确终态。

仓库中的代码、规格、ADR、测试和检查结果是长期事实来源。对话、隐藏推理、临时计划和旧 patch 不能代替这些资产。

## 2. 核心原则

1. **事实先于方案**：可以从仓库、上游源码或官方资料获得的信息，由 Agent 先行调查。
2. **规格先于非平凡实现**：行为、格式、架构或兼容性变化先形成工作契约。
3. **一个切片一个结果**：默认只有一个进行中的代码实施工作项。
4. **证据匹配风险**：静态检查不能证明运行时行为，单元测试不能证明真实 Zed build。
5. **机器门禁优先**：可机械验证的约束进入测试或 CI，不长期依赖提示词提醒。
6. **人类拥有关键决定**：AI 可以提出和实现，用户确认范围扩张、不可逆操作与发布。
7. **显式终态**：工作项结束于 `completed`、`blocked`、`cancelled` 或 `superseded`，不能长期停留在模糊的“基本完成”。

## 3. 任务分级

### 3.1 轻量任务

满足以下全部条件时，可以不创建工作项：

- 只涉及局部、机械且低风险的修改；
- 不改变外部行为、持久格式、公共 CLI、架构或工程流程；
- 验收可以通过一个聚焦检查明确证明。

仍然必须检查 Git 状态、保持范围并报告验证结果。

### 3.2 非平凡任务

出现任一情况时，在 `docs/work/active/` 创建工作项：

- 新增或改变用户可观察行为；
- 修改 parser、语义规则、rewrite、版本对账或 runtime；
- 引入依赖、生成格式或新的跨模块关系；
- 修复需要根因调查的缺陷；
- 改变测试、CI、发布或 AI 工作流程。

涉及长期架构、兼容性或持久格式的决定，还要新增或更新 `docs/decisions/` 中的 ADR。

## 4. 标准生命周期

```text
调查 → 工作契约 → 实施计划 → 小范围实现
  → 聚焦验证 → 完整相关门禁 → 独立复核
  → 收敛修正 → 完成或明确终止
```

### 4.1 调查

Agent 在提出方案前确认：

- 当前 Git 状态和已有用户改动；
- 权威文档、相关 ADR 和当前工作项；
- 真实源码、测试和外部接口；
- 已确认事实、推断、未知信息和验证方式。

外部调研记录调查日期、来源链接或 commit，并区分官方事实、社区实验和本项目推断。

### 4.2 工作契约

工作项必须写清：

- 要解决的问题和可观察结果；
- 修改范围与非目标；
- 已确认事实和关键假设；
- 可执行或可观察的验收条件；
- 预期证据及不能运行时的降级方式。

验收条件不能只写“实现功能”“测试通过”或“代码质量良好”。

### 4.3 实施计划

计划按可独立验证的顺序拆分，标明：

- 每步改变的资产；
- 前置依赖；
- 失败时停止条件；
- 对应验证命令。

复杂非机械 diff 以约 500 行为软性 review budget。超过时根据实际依赖拆分，而不是为了数字机械切割同一个原子变化。

### 4.4 实现

- 只修改当前工作项授权的范围；
- 不进行 drive-by cleanup；
- 新行为与聚焦测试在同一切片交付；
- 生成物只通过拥有它的生成器更新；
- `local/zed` 保持只读，Overlay 写入独立派生工作区；
- 遇到会改变目标、公共格式或安全边界的未知信息时停止并请求决定。

### 4.5 验证

先运行最接近变化的聚焦测试，再运行 `uv run python scripts/check.py`。领域专属证据见[测试策略](testing.md)。

验证记录至少包含：

| 字段 | 含义 |
| --- | --- |
| 命令或操作 | 实际执行的完整命令或 UI 操作 |
| 结果 | passed、failed、blocked 或未运行 |
| 证明内容 | 对应哪个验收条件 |
| 环境 | Python/Zed commit、平台或关键配置 |
| 限制 | 该证据没有证明什么 |

### 4.6 独立复核与收敛

高风险或跨边界修改使用新的只读上下文复核：

- 实现是否满足工作契约而非仅满足代码结构；
- 是否改变范围外行为；
- 测试是否能在缺少保护时失败；
- 文档、schema、fixtures 与实现是否一致；
- 是否存在未经说明的兼容性或隐私影响；
- 是否留下临时文件或 dirty generator output。

复核先输出 findings；修复后重新运行受影响验证，直到所有验收条件有证据或工作项进入明确终止状态。

## 5. 人类确认点

以下操作必须由用户明确授权：

- 扩大工作项目标或修改已经确认的非目标；
- 采用新的长期架构、持久格式或兼容性承诺；
- 删除或覆盖难以恢复的数据；
- 修改 `local/zed`、外部仓库或远程系统；
- Git commit、push、tag、发布和 Release；
- 使用真实凭据、付费服务或生产数据。

范围内的源码编辑、只读调查和本地聚焦检查不需要重复确认。

## 6. 多 Agent 协作

- 同一工作树同一时刻只有一个写入者。
- 并行 Agent 优先承担只读调查、独立 review 或互不重叠的工作树任务。
- 派发任务必须包含工作项、精确路径、禁止范围、验收条件和返回证据。
- reviewer 默认只报告 findings，不与 implementer 同时修改相同文件。
- 多 Agent 结论冲突时回到源码、测试和规格，不通过投票决定事实。

## 7. 规则与 skill 的演进

新规则只有同时满足以下条件才进入 `AGENTS.md`：

1. 熟悉代码的人也可能误判；
2. 已重复出现或影响重大；
3. 可以写成具体动作；
4. 不能更可靠地由测试或 CI 替代。

仅适用于特定任务且流程已经重复验证的知识，才固化为 `.agents/skills/`。一次性发现记录在工作项或 ADR，不立即变成全局规则。

## 8. 交付格式

Agent 最终交付按重要性说明：

1. 已实现的结果；
2. 关键设计和兼容性影响；
3. 验证命令及结果；
4. 未运行项目与剩余风险；
5. 相关文件和 Git 状态边界。

不得把“代码看起来正确”“预计可以通过”写成已经验证。
