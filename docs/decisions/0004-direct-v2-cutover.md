# ADR 0004：直接切换 corpus v2

Status: accepted

## 问题

阶段 0.5 已建立能够支持精确评分的 corpus v2，但初始实现仍冻结 v1 并保留读取、校验和迁移能力。项目尚未发布，也没有外部数据兼容承诺。此时维持两套 schema 会让阶段 1 的公共 API、测试矩阵和错误处理承担没有实际用户价值的复杂度。

## 决定

项目直接切换到 schema version 2：

- v2 是唯一可读、可校验和可评估的 corpus；
- 删除 v1 corpus、schema、Python 模型、测试和版本分派；
- Python API 使用无版本后缀的 `GoldenCorpus`、`load_corpus` 和 `validate_checkout`；
- manifest 继续显式记录 `schema_version: 2`，未知版本严格拒绝；
- 不提供 v1 到 v2 的运行时兼容层或仓库内迁移入口。

阶段 0 的调查结论和历史工作项可以保留对 v1 的事实性描述，但不得把 v1 表述为当前受支持资产。

## 备选方案

- 长期保留 v1 只读支持：适合已发布且存在外部数据的项目，但当前没有对应消费者，只会扩大维护面。
- 保留一次性迁移 CLI：能够帮助未知本地数据，但会要求永久保留 v1 解析模型；当前 corpus 已完成切换，没有这一需求。
- 将 v2 重新编号为 v1：表面上更简洁，但会抹去已记录的 schema 语义变化，使历史数据和 ADR 难以解释。

## 后果

- 阶段 1 只需实现一种 corpus 与评估协议。
- 当前源码和数据边界更小，不存在版本联合类型和兼容分支。
- 任何 v1 私有副本不能由当前工具读取；需要时只能使用对应历史 Git revision 或编写仓库外一次性转换。
- schema version 仍保留为 2，未来真实兼容需求必须通过新的 ADR 决定。

## 验证

- 搜索当前源码、脚本、schema 和测试，不存在 v1 解析或版本分派。
- 默认 corpus 校验 266 条 v2 样本和固定 Zed checkout。
- Ruff、ty 和 pytest 完整门禁通过。
- `local/zed` 内容和 Git 状态保持不变。

## 重新评估条件

- 项目发布后需要支持多个 corpus schema 的滚动升级。
- 出现不能在发布边界外一次性迁移的持久用户数据。
- 外部工具正式依赖本项目的 corpus 读取 API。
